### 核心公式与复合概率法则
1. **Agent 核心公式**：
   $$\text{Agent} = \text{Model（引擎）} + \text{Harness（外围底盘、刹车与仪表盘）}$$
   大模型负责概率决策，Harness 负责上下文装配、格式校验、工具沙箱、状态机与安全纠偏。
2. **复合概率诅咒（Compounding Error）**：
   $$Pass^k = p^k$$
   单步准确率 $p=95\%$（0.95），连续执行 10 步的端到端成功率仅剩 **59.8%**（$0.95^{10}$）。**商业级 Agent 的本质，就是用确定性的 Harness 工程对抗模型单步不确定性的复合放大。**

## 第 1 章 基本概念与运行时：Agent 是怎样跑起来的？

### 【技术底层与实现】
1. **大模型的物理本质：绝对无状态（Stateless）**
   - 形象比喻：**“只要眨眼就失忆的天才外科医生”**。物理上大模型是纯数学函数 $\text{Next\_Token} = f(\text{Context})$。
   - 运行时真相：每一次与大模型交互，系统都必须在背后将**包含 System、User、Assistant、Tool 返回结果的全量历史重新组装成 JSON，全量打上网络发给云端 API**。
2. **Prefill（首字计算）与 Decode（逐字生成）**
   - **Prefill 阶段**：GPU 并行吞入上万输入 Token 计算注意力矩阵，导致产生秒级的**首字延迟（Time to First Token, TTFT）**。
   - **Decode 阶段**：首字出来后，基于显存中的 KV Cache 逐字线性自回归生成，速度平稳。
3. **最小 Agent 运行时（30 行 Python 代码原型）**
   ```python
   import json
   from openai import OpenAI
   client = OpenAI()

   def run_agent_loop(query, system_prompt, tools_schema, tool_map):
       messages = [{"role": "system", "content": system_prompt}, {"role": "user", "content": query}]
       for _ in range(10): # 10 步硬熔断
           res = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools_schema)
           msg = res.choices[0].message
           messages.append(msg)
           if not msg.tool_calls:
               return msg.content # 给出最终答复，退出
           for tc in msg.tool_calls: # Harness 执行工具
               fn, args = tool_map[tc.function.name], json.loads(tc.function.arguments)
               result = fn(**args)
               messages.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(result)})
   ```

### 【产品架构与落地】
1. **工作流（Workflow）vs 自主 Agent（Agentic）选型决策**：
   - 路径明确、规则固定（<5 步）：坚决做确定性工作流或路由（Router），稳定度 >99%，成本最低；
   - 路径发散、需根据外部反馈动态决策：做 ReAct 自主 Agent，但必须强加单任务最大轮数（Max Steps）和超时硬熔断。
2. **ACI（Agent-Computer Interface）防呆原则**：
   - 给 Agent 用的工具不能直接复用给前端用的 REST API，必须参数扁平化、宽容解析，并在描述中写死错误反例。

## 第 2 章 上下文工程：Agent 的眼睛与成本命门

### 【技术底层与实现】
1. **KV Cache 显存原理与 Prompt Cache（前缀树缓存）**
   - KV Cache 物理内存公式：$\text{显存} = 4 \times n_{\text{layers}} \times n_{\text{heads}} \times d_{\text{head}} \times \text{上下文长度} \times \text{并发}$。
   - Prompt Cache 命中规则：云厂商按 Radix Tree（基数树）匹配，**必须从第 1 个字符开始完全一致**。
   - 命中则享受 **1 折成本与超低 TTFT 延迟**；击穿则全额扣费并忍受卡顿。
2. **现代状态机编程模型（LangGraph 架构）**
   - 生产级 Agent 绝非单个 Prompt，而是基于图状态机（StateGraph）。
   ```python
   # 定义不可变状态追加机制
   class AgentState(TypedDict):
       messages: Annotated[Sequence[BaseMessage], add_messages]
       require_approval: bool
   ```

### 【产品架构与落地】
1. **前缀静止铁律**：
   - System Prompt 和工具 Schema 必须在字节级别保持绝对不变！严禁在开头插入动态时间戳（如 `当前时间: 15:30`），动态参数必须追加在末尾消息中。
2. **Agent Skills 渐进式披露（Progressive Disclosure）**：
   - **L0 目录层**：常驻 System Prompt，每项技能仅 1 行说明（~200 Token）；
   - **L1 技能层**：当用户意图命中时，按需加载该技能的详细约束规则与工具参数（~1000 Token）；
   - **L2 隔离层**：任务执行完即清理，避免海量细则挤爆后续会话。
3. **状态栏（Status Bar）设计模式**：
   - 在每轮输入最末端由代码追加显式状态：`<status>目标:退款 | 步数:3/8 | 报错:2次(重试请换参数)</status>`，将隐式分布的长记忆转为显式先验，降低 80% 死循环。
4. **隔离胜过压缩**：海量数据探索任务委托给独立临时子 Agent，主会话只收精简报告，拒绝全量文本摘要。

## 第 3 章 记忆与知识体系：跨越会话的持久化智能

### 【技术底层与实现】
1. **混合检索流水线（Hybrid Search + RRF）**
   - 单一向量（Bi-Encoder）像“看相亲简历”，无法理解零件型号与逻辑反转；
   - 工业级方案：**BM25（精准词频）+ 稠密向量（泛化语义）双路召回 $\to$ RRF 融合 $\to$ Cross-Encoder 深度重排**。
   - RRF 算法：$RRF\_Score(d) = \sum \frac{1}{60 + \text{在该路检索里的排名}}$，只看排名次序，打通不同量纲。
2. **Contextual Chunking（上下文感知切分）**
   - 离线切块时调用小模型给每个切片头部嵌入 50~100 字文档全局背景说明，彻底治愈代词丢失，召回率提升 35%。

### 【产品架构与落地】
1. **记忆的三层体验阶梯**：
   - 显式偏好（个人中心可查可改） $\to$ 跨会话检索（根据历史资料延展工作） $\to$ 主动服务（高置信度下提前推送）。
2. **记忆变更的“PR（Pull Request）”离线闭环**：
   - **严禁在线对话时直接改写画像库！** 
   - 必须走在线提议（Proposer） $\to$ 写入待审暂存区 $\to$ 夜间离线 Worker（睡眠学习）核验冲突、敏感信息脱敏 $\to$ 合并入库。

## 第 4 章 工具体系：给 Agent 配备安全的手脚

### 【技术底层与实现】
1. **Grammar 约束解码底层原理**
   - 大模型本质只会吐字，推理引擎通过 BNF 状态机动态构建 Token 掩码，在每步生成时把所有违反 JSON 语法的字符概率强制 Mask 为 0，确保输出 100% 合法格式。
2. **MCP（Model Context Protocol）标准协议**
   - 基于 JSON-RPC 2.0，涵盖 Prompts、Resources、Tools 三大原语，成为 AI 时代的“USB 标准”。
3. **沙箱四层物理隔离体系**
   - 命名空间隔离（只看指定目录） $\to$ Cgroups 限制（内存/CPU/超时） $\to$ iptables 出站白名单 $\to$ gVisor / Firecracker 内核级轻量虚拟化阻断。

### 【产品架构与落地】
1. **工具描述反例与边界**：描述不仅要写“能干什么”，更要写“什么时候绝对不要用它”。
2. **幂等性保障（Idempotency Key）**：涉及转账、下单、发信的写操作工具，必须在客户端生成全局唯一 Key，防止 Agent 重复重试导致连扣多笔款项。
3. **Sidecar 旁路审核**：主模型流式输出的同时，轻量小模型毫秒级并行审查入参危险度。

## 第 5 章 Coding Agent：通用 Agent 的底层内核

### 【技术底层与实现】
1. **为什么通用 Agent 底层都是写代码？**
   - 代码是人类最精确的形式化工具：算账用 Python 算（准确率 100%）、调接口写脚本（替代几十轮自然语言交互）。
   - 软件工程几十年现成的基建（Linter、编译器报错、单元测试、Git 回滚）提供了世界上最完美的 Harness。
2. **Search-and-Replace 唯一子串原位替换**
   - **行号漂移灾难**：让模型输出“在第 45 行修改”不可靠，前面的任何编辑都会导致后续行号错位；全量重写大文件又极耗 Token 且易截断。
   - **工业级标准（Aider / Claude Code 范式）**：让模型仅输出具备唯一性的局部修改块：
     ```text
     <<<<<<< SEARCH
     def calculate_tax(amount):
         return amount * 0.1
     =======
     def calculate_tax(amount, is_vip=False):
         rate = 0.05 if is_vip else 0.1
         return amount * rate
     >>>>>>> REPLACE
     ```
   - 底层 Harness 在目标文件中全文搜索 `SEARCH` 块，命中且唯一则原位替换为 `REPLACE` 块；若未命中则降级为 Levenshtein 模糊匹配或 AST（抽象语法树）节点定位。
### 【产品架构与落地】
1. **代码生成 vs 生成模型边界**：
   - 工业零件、带精细排版的 PPT、报表图表走代码生成（精准、可调试）；
   - 人脸、自然风光等无限细节走 Diffusion/生成模型。
2. **权限下沉至数据层**：动态生成代码的执行权限，必须下沉到数据库行级安全策略（RLS），代码写错也无法越权。

## 第 6 章 交互扩展：观察与动作空间的扩展

### 【技术底层与实现】
1. **交互五大系统原语**：
   $$\text{交互原语} = \{\text{唤醒}, \text{安全点}, \text{取消}, \text{抢占}, \text{快慢分离}\}$$
2. **GUI 视觉定位（Grounding）技术路线**：
   - **路线 A（Set-of-Mark）**：截屏打上半透明红框与数字标号，送入视觉大模型输出点击编号；
   - **路线 B（Accessibility Tree）**：提取网页/手机无障碍语义树为极简文本结构直接定位坐标（网页端首选，省 Token 且准）。

### 【产品架构与落地】
1. **动作后必有状态闭环（Verify State）**：GUI 点击或硬件指令发出后，**严禁假设执行成功**，必须重新截屏或查库校验真实状态迁移。
2. **前台毫秒级先行安抚（快慢分离）**：复杂任务触发时，前台 200ms 内触发语音或动效安抚（“正在为您查询…”），掩盖后台几秒钟的 Agent 多步调度。

## 评估基石：以科学评估建立可度量反馈（第 7 章）

没有评估体系的 Agent 迭代就像在黑暗中射击。

### 【技术底层与实现】
1. **评估环境五要素**：
   $$\text{评估系统} = \text{任务数据集} + \text{可重置环境状态} + \text{原子工具集} + \text{评分量表 (Rubric)} + \text{交互终止协议}$$
2. **两层回归任务体系**：
   - **端到端回归**：检验全链路综合表现是否退化；
   - **轨迹前缀回归（Prefix Regression）**：冻结前 N 步正确轨迹，专门考验第 N+1 步在边缘条件下的决策边界。
3. **统计显著性检验**：模型评估对比必须使用配对检验（McNemar 检验 / Bootstrap 配对抽样），跨过纯随机波动的噪声。

### 【产品架构与落地】
1. **商业指标的照妖镜：Pass@k vs Pass^k**：
   - $Pass@k$（尝试 $k$ 次成 1 次）：学术界与发布会 Demo 刷脸指标；
   - $Pass^k$（连续 $k$ 次都不能错）：商业客户付费的唯一真实门槛。
2. **归因定位首错（First Mistake）**：失败分析坚决不能看最后报错的红字，必须倒推定位导致偏航的**第一个动作**。
3. **LLM 裁判去偏**：采用异构模型交叉评判，强制对调展示顺序消除位置偏见，并在 Rubric 中设置造假、泄露等一票否决项。

## 层面一 · 模型参数扩展：模型后训练（第 8 章）

### 【技术底层与实现】
1. **后训练四阶段全景**：
   - 预训练（通识接龙书呆子） $\to$ Mid-training（补充长上下文与领域底座） $\to$ SFT（格式与上岗培训） $\to$ RL（考场探索泛化）。
2. **SFT 训练细节：Loss Masking（损失掩码）**
   - 仅对大模型自主思考与工具参数计算梯度损失，用户输入与工具返回结果权重置 0，防止模型死背外部输出。
3. **RLVR 与 GRPO 核心原理（DeepSeek-R1 的秘密）**
   - **RLVR**：以代码编译器、单元测试等冷酷的**确定性验证器**为考官，告别主观打分；
   - **GRPO（群组相对策略优化）**：彻底剔除传统 PPO 庞大的打分员模型（Critic），单题采样 8 组解法计算相对得分，显存砍半，吞吐提升 3 倍。

### 【产品架构与落地】
1. **分工定位**：**“SFT 记忆，RL 泛化；数据与环境比算法更重要。”** SFT 教会模型按正确格式输出，RL 逼出模型的纠偏与自我长链推理能力。
2. **防范奖励黑客（Reward Hacking）**：验证环境必须对模型不可见（隐藏单元测试），防止模型用投机取巧手段骗取正向奖励。

## 层面二 · 单体系统扩展：基于经验的持续进化（第 9 章）

大模型不能也不应该在线实时更新权重（极易造成策略崩溃和不可逆安全事故）。

### 【技术底层与实现】
1. **在线离线双循环架构（睡眠学习）**：
   ```mermaid
   flowchart LR
       Online[在线系统: 仅执行任务<br>不可变写入审计日志] -->|回流轨迹| DB[(生产日志池)]
       DB --> Offline[离线睡眠学习: 聚类挖掘 Badcase<br>提炼最小 Prompt/Skill 补丁]
       Offline --> TestGate{双集验证门禁}
       TestGate -- 达标 --> Canary[灰度上线]
   ```
2. **代码化硬约束优先**：能用代码和 Schema 约束拦截的业务边界，绝不在 Prompt 里写小作文。

### 【产品架构与落地】
1. **保存经历 ≠ 从经历中学习**：堆积大量会话日志毫无意义，真正的进化在于对成功与失败的多轨迹对照挖掘与提炼。
2. **双集验证门禁机制**：
   - **边界集（Boundary Set）**：验证以前出过问题的 Case 是否被修好；
   - **保留集（Retain Set）**：监控原有基准表现，严防过度矫正导致既有能力退化。
3. **可信根隔离**：Agent 有权提议修改业务规则或优化 Skill，但**决无权修改自身的评测用例与发布门禁**。

## 层面三 · 群体系统扩展：多 Agent 协作（第 10 章）

多 Agent 协同是概念炒作最重、翻车率最高的领域。

### 【技术底层与实现】
1. **多 Agent 本质是分布式操作系统**：
   $$\text{LLM}=\text{CPU}, \quad \text{上下文}=\text{进程内存}, \quad \text{提示词}=\text{程序}, \quad \text{文件}=\text{IPC 通信接口}$$
2. **跨进程通信三大机制**：工具调用参数（同步阻塞）、共享文件系统（工作区/隔离区）、消息总线（异步 Pub/Sub）。
3. **A2A（Agent-to-Agent）跨组织协议**：
   - 依赖标准化 Agent Card（能力声明）与状态机，仅交换产物而不暴露内部长轨迹。

### 【产品架构与落地】
1. **多 Agent 增益的唯一判据**：
   > **多 Agent 协作优于单 Agent 的唯一前提，是这种协作是否引入了外部的“新信息”反馈！**
   - 伪需求：两个语言模型在那儿互相做纯文本自我辩论（盲区一致，白耗 Token）；
   - 真需求：Proposer 负责写代码，环境执行报错，Reviewer 看着**真实报错和渲染截图**进行审核。
2. **防范新型系统崩溃模式**：
   - 并发写冲突（必须引入乐观锁或 Git 分支隔离）；
   - 相互推诿与死循环（配置全局步骤预算与强制终止上下文 Context）；
   - 人类的“认知投降”（面对庞大的多 Agent 链路彻底失去代码可读性与架构把控）。

## 模块一：人在回路（HITL）的三种产品接入形态

```
模式 A: 动作前强授权 (Pre-action Approval)
Agent 界面弹出卡片：“即将从您的账户扣款 450 元购买车票”，用户点击【确认支付】后才下发 API。

模式 B: 悲观降级接管 (Pessimistic Fallback)
当置信度低于 0.7、或连续 2 步工具调用报错时，界面无缝切为人工客服会话，带入历史完整上下文。

模式 C: 动作后事后审计 (Post-action Undo)
操作直接生效，但系统保留 5 分钟的“撤销（Undo）”缓冲窗口并推送通知。
```

## 附录：技术 PM 专属 PRD 检查清单（20 条硬核自查项）

在召集技术、算法召开方案评审会前，请逐条对照自查：

### 架构与成本
- [ ] 1. 系统提示词（System Prompt）和工具 Schema 是否完全固化，绝无拼接当前时间戳等动态变量？
- [ ] 2. 是否为单任务配置了最大轮数（Max Steps）和超时时间（Timeout）硬熔断？
- [ ] 3. 大量非高频技能是否设计了 Skills 渐进式加载（L0/L1/L2）架构，避免工具一次性撑爆上下文？
- [ ] 4. 处理海量背景资料检索时，是否采用了子 Agent 物理隔离机制，防止主上下文被脏数据污染？
- [ ] 5. 长文本工具返回（如日志、SQL 查询全量结果）是否在工程层做了首尾截断并落盘处理？

### 工具与接口（ACI）
- [ ] 6. 工具入参设计是否面向 Agent 拍平？是否存在复杂的深度嵌套 JSON？
- [ ] 7. 工具描述中是否明确写出了“何时严禁调用”的反例与边界？
- [ ] 8. 涉及资金划扣、发信、数据修改的写操作工具，是否全部配置了唯一的幂等 Key（Idempotency Key）？
- [ ] 9. 工具代码执行环境是否置于隔离的沙箱（Docker / gVisor）中，并切断了无关的外网访问？
- [ ] 10. 高危敏感操作是否设计了人在回路（HITL）确认卡片或独立模型的二次校验（Reviewer）？

### 交互与安全
- [ ] 11. 在 GUI 自动化或真实环境执行动作后，是否强制通过下一轮观察（截图/接口查库）闭环验证了状态？
- [ ] 12. 前端交互是否支持用户单向随时打断（Barge-in / Cancel），打断后后台的级联异步进程是否能即时销毁？
- [ ] 13. 高频简单指令是否设计了快慢双通道，绕过复杂的 Agent 编排直达端侧执行？
- [ ] 14. 检索到的非受信任外部网页/文本，是否打上了数据隔离标签，防止间接提示词注入攻击？
- [ ] 15. 系统核心权限是否下沉至数据层（数据库行级安全策略），而非依赖大模型在代码逻辑中自行把关？

### 记忆、评测与演化
- [ ] 16. 用户长期记忆是否通过离线任务（PR 模式）异步清洗、去重和合并，绝不在线实时强行覆写？
- [ ] 17. 产品评估不仅看单次成功率 $Pass@k$，是否量化监控了反映连续可用性的 $Pass^k$ 指标？
- [ ] 18. 失败分析时，归因漏斗是否锁定了导致最终偏离的“首个错误（First Mistake）”，而非末端报错？
- [ ] 19. 提示词与模型升级是否配置了包含“边界集”与“保留集”的自动化回归流水线？
- [ ] 20. 架构中拆分的多 Agent，每一个角色是否确实能够带来代码编译、真实工具输出等“外部新信息反馈”？
